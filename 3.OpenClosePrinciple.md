A software entity should always be open for extension and closed for modification
Software entity means - class, module, component, function, etc.

Example, you have working code for 3 payment methods, tomorrow if you want to add a new payment option, then you shouldn't be modifying an existing 'PaymentProcessor' class with a new if-else statement to accommodate that.

With a good OCP-implementation, you would be easily able to add a new implementation of processing the payment without changing any existing code.

Why do we need OCP?
The existing code is valuable once it has been tested and used in prod. 
If adding a new requirement constantly forces you to modify existing stable code, that is where you should start thinking about OCP.
The easiest way to identify OCP being broken is when a class getting modified whenever a new kind of something is getting added

### Solution:

Instead of:

```cpp
if (type == "UPI") {
    ...
}
else if (type == "CARD") {
    ...
}
```

we can define an abstraction:
``` cpp
class PaymentMethod {
public:
    virtual void pay() = 0;
    virtual ~PaymentMethod() = default;
};
```
Then:
``` cpp
class Card : public PaymentMethod {
public:
    void pay() override {
        // Card payment
    }
};
```
Now the code using `PaymentMethod` does not need to know the specific payment type.

If tomorrow you add:
``` cpp
class Wallet : public PaymentMethod {
public:
    void pay() override {
        // Wallet payment
    }
};
```
you have extended the system rather than modifying the existing payment implementations.

That is OCP working together with polymorphism.

You can also use Strategy design Pattern which is actually similar to what we studied, so dw about it
And the same thing goes with abstraction and composition, they all do the same thing, just different names

### OCP does not mean you should abstract everything
``` cpp
class Calculator {
public:
    int add(int a, int b) {
        return a + b;
    }
};
```
You don't need to create:
```
Operation
 ├── Addition
 ├── ...
```
just because someone might someday add subtraction. That would be overengineering. A good designer thinks about where variation is actually expected. For example, payment methods, notification channels, discount rules, storage mechanisms, and authentication methods are often naturally variable. A simple add() function usually isn't.

### OCP is not about abstracting everything
It is about what things are likely to change rather than what things could be extended. Everything could be extended, but will it extend or is there any possible for it extend in future? So, even if something can be extended but it is very static and has very less possibility of getting extended in future, there is no point in complicating the code just for the sake of following OCP. Things which have the possibility to extend are expected to follow OCP, not everything. It is about protecting the parts of the code that are likely to change.
