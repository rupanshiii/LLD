# Inheritance vs Composition in LLD

In LLD questions, one of the most confusing decisions is:

> **Should I use inheritance or composition? And why?**

The confusion usually comes from the basic definitions:

* **Inheritance → IS-A relationship**
* **Composition → HAS-A relationship**

The problem is that identifying which relationship actually fits a design is not always obvious.

In fact, **the same two classes can sometimes be connected through inheritance in one design and composition in another**, depending on what we are trying to model.

So let's make the distinction clearer.

---

# 1. The Obvious Case: Shape

Suppose we have a `Shape` class and different types of shapes:

```text
Shape
├── Circle
├── Triangle
└── Square
```

At first glance, this seems like an obvious inheritance relationship:

```text
Circle IS-A Shape
Triangle IS-A Shape
Square IS-A Shape
```

So inheritance appears to be the natural choice.

But now let's think about what `Shape` actually contains.

Suppose `Shape` has properties such as:

* Number of sides
* Dimension
* Volume
* Area
* Curvature
* etc.

The problem is that **not every shape has every property**.

For example:

### Circle

A circle has:

* 2 dimensions
* Area
* Curvature

But it does not have:

* Sides
* Volume
* 3rd dimension

Similarly, a 3D shape may have:

* Volume
* 3 dimensions

but may not have the same properties as a circle.

So if we force everything into one large `Shape` hierarchy, subclasses may end up inheriting properties or behaviors that don't actually make sense for them.

This is where inheritance can become problematic.

---

# 2. Problem: Tight Coupling

With inheritance, the child class becomes strongly dependent on the parent class.

```text
Shape
  ↑
Circle
```

If we modify `Shape`, the changes can potentially affect `Circle` and all other subclasses.

For example, suppose we add a new property or behavior to `Shape`.

Now every child class has to deal with that addition, even if the new functionality is not meaningful for that particular shape.

This creates **tight coupling between the parent and its children**.

The more responsibilities we put into the parent, the more difficult it becomes to maintain the entire hierarchy.

---

# 3. Problem: Inheritance Makes a Strong Promise

When we create:

```text
Bird
  ↑
Penguin
```

we are saying:

> **Penguin is a Bird.**

But inheritance often means more than just this statement.

The child is also expected to satisfy the behavioral contract of the parent.

For example, imagine:

```text
Bird
└── fly()
```

Now:

```text
Penguin → Bird
```

A penguin is certainly a bird, but it cannot fly.

This creates a problem if the parent abstraction assumes:

> "Every Bird can fly."

The issue is not that the real-world relationship is incorrect.

The issue is that **the abstraction chosen for the parent is too broad or imposes behavior that does not apply to every child.**

This is one reason inheritance should not be used merely because an `IS-A` relationship exists in the real world.

The question is:

> **Does the child genuinely satisfy the abstraction and behavioral contract of the parent?**

---

# 4. Problem: Inheritance Does Not Handle Combinations Well

Another major problem appears when we have multiple independent behaviors.

Suppose we have robots with different capabilities.

### AllRounder Robot

```text
Flying
Walking
Talking
Cooking
```

### Drone Robot

```text
Flying
Walking
```

### Chef Robot

```text
Walking
Talking
Cooking
```

We might initially try to model this using inheritance:

```text
Robot
├── FlyingRobot
│   └── ...
├── WalkingRobot
│   └── ...
├── TalkingRobot
│   └── ...
└── CookingRobot
    └── ...
```

But soon we need to represent combinations:

```text
Flying + Walking
Walking + Talking + Cooking
Flying + Walking + Talking
Flying + Cooking
...
```

If every combination becomes a separate subclass, the number of classes can grow rapidly.

We could end up with classes such as:

```text
FlyingWalkingRobot
WalkingTalkingRobot
WalkingTalkingCookingRobot
FlyingWalkingTalkingRobot
FlyingWalkingCookingRobot
...
```

As the number of independent capabilities increases, the number of possible combinations grows dramatically.

This leads to:

* Too many classes
* Deep or complicated hierarchies
* Difficult maintenance
* Difficult reasoning about which class should be used
* Poor scalability when new behaviors are introduced

In other words:

> **Inheritance is good at representing a hierarchy, but it is not good at representing arbitrary combinations of independent behaviors.**

---

# 5. This Is Where Composition Helps

Instead of creating a new class for every combination, we can treat each capability as an independent component.

For example:

```text
Robot
├── MovementBehavior
├── CommunicationBehavior
└── CookingBehavior
```

And then provide different implementations:

```text
MovementBehavior
├── Walk
├── Fly
└── Swim

CommunicationBehavior
├── Talk
└── NoCommunication

CookingBehavior
├── CanCook
└── CannotCook
```

Now we can construct different robots by combining the behaviors they need.

### AllRounder

```text
Robot
├── Walk
├── Talk
├── Fly
└── Cook
```

### Drone

```text
Robot
├── Walk
└── Fly
```

### Chef

```text
Robot
├── Walk
├── Talk
└── Cook
```

We don't need a new class for every possible combination.

This is the real strength of composition.

---

# 6. The Important Distinction

The key question is not simply:

> **"Is this an IS-A relationship?"**

Instead, ask:

> **"What exactly am I trying to model?"**

If I am modeling a **stable type hierarchy**, inheritance can be appropriate.

```text
Circle IS-A Shape
Dog IS-A Animal
Circle IS-A Shape
```

But if I am modeling **capabilities, behaviors, or replaceable components**, composition is often more suitable.

```text
Robot HAS-A FlyingBehavior
Robot HAS-A WalkingBehavior
Robot HAS-A CookingBehavior
```

So a useful mental model is:

```text
Inheritance
    ↓
"What is this object?"
    ↓
Stable specialization / polymorphism

Composition
    ↓
"What does this object have or what can it do?"
    ↓
Independent / replaceable behaviors and components
```

---

# 7. Why Do People Say "Prefer Composition Over Inheritance"?

This statement does **not** mean that inheritance is bad.

It means:

> **When both approaches can solve the problem, composition often provides more flexibility and less coupling.**

Inheritance creates a strong relationship between parent and child.

Composition allows us to assemble an object from independent components.

Therefore, composition is particularly useful when:

* Behavior can change independently
* Components need to be swapped
* Multiple behaviors need to be combined
* We want to avoid deep inheritance hierarchies
* We don't want a child to depend heavily on the implementation of its parent

Inheritance is still very useful when:

* There is a genuine subtype relationship
* The hierarchy is stable
* The child truly satisfies the parent's behavioral contract
* We need polymorphism through a common abstraction

---

# 8. The Question to Ask in an LLD Interview

When you're unsure between inheritance and composition, ask yourself:

> **"Am I creating a new type, or am I combining/replacing a behavior?"**

### Creating a genuine new type

```text
Shape
├── Circle
├── Square
└── Triangle
```

→ **Inheritance can make sense.**

### Combining or changing behaviors

```text
Robot
├── Flying
├── Walking
├── Talking
└── Cooking
```

→ **Composition is usually a better fit.**

The goal is not to blindly prefer one over the other.

The goal is to choose the relationship that **best represents the responsibility and the way the system is expected to evolve.**

## Scenarios

1. Payment Methods

Question:

Suppose a payment system supports UPI, Credit Card, Debit Card, Net Banking, and Wallet. The checkout system should be able to work with any payment method without knowing which specific payment method it received. Which relationship should we use?

Answer:

Inheritance or an interface is suitable because UPI, Credit Card, Debit Card, and the other methods are all different implementations of the same concept, which is a PaymentMethod.

The important reason is polymorphism. The checkout system can work with the common PaymentMethod type and call its payment operation without caring about the concrete implementation.

The main clue is that we have multiple implementations of the same concept, and we want to treat them uniformly.

2. File Storage

Question:

Suppose an application supports Local Storage, Amazon S3, Azure Blob Storage, and Google Cloud Storage. The application should be able to switch the storage system through configuration without changing the document-processing logic. Which relationship should we use?

Answer:

This might initially look like composition because the storage can be changed through configuration. However, configuration-based switching alone does not mean that composition is required.

LocalStorage, S3Storage, AzureStorage, and GoogleStorage are all implementations of the same Storage abstraction. Therefore, inheritance or an interface is useful for representing these different implementations.

At the same time, the component that uses storage can contain a Storage object. That is composition.

So there are actually two relationships here. S3Storage is a Storage, which uses inheritance or interface polymorphism. DocumentProcessor has a Storage, which uses composition.

The main lesson is that we should look at the relationship between the objects instead of deciding that the entire problem must use only inheritance or only composition.

3. Ride Sharing

Question:

Suppose a Driver has a vehicle. The vehicle can be a Car, Bike, or Auto. A driver might use a car today and a bike tomorrow. Which relationship should we use between Driver and Vehicle?

Answer:

Composition is suitable because the vehicle does not define the type of Driver.

A driver can use a car today and a bike tomorrow without becoming a different type of driver. Therefore, the vehicle can change independently of the Driver.

We can make Driver contain a Vehicle object and change the vehicle when required.

There can still be inheritance inside the vehicle hierarchy. Car, Bike, and Auto can all implement or inherit from Vehicle because they are different types of vehicles.

So Driver has a Vehicle, which is composition, while Car is a Vehicle, which can use inheritance.

The strongest clue is that the component can change independently without changing the identity or type of the main object.

4. Notifications

Question:

Suppose a user can receive notifications through Email, SMS, and Push Notification. A user can have Email and SMS enabled at the same time, then enable Push Notification later, and disable any channel independently. Which relationship should we use?

Answer:

Composition is suitable because these notification channels are independent capabilities that can be combined.

It would be a poor design to create classes such as EmailUser, SMSUser, EmailSMSUser, EmailPushUser, and EmailSMSPushUser. The number of classes would keep growing as more notification channels and combinations are added.

Instead, the user or notification system can contain multiple notification-channel objects and use whichever channels are currently enabled.

There can still be a common NotificationChannel interface, with EmailNotification, SMSNotification, and PushNotification as its implementations. That part uses inheritance or interface polymorphism.

However, the relationship between the notification system and the channels is composition because multiple independent channels can be combined and changed independently.

The main clues are that multiple independent behaviors can exist together and those behaviors can be enabled, disabled, or changed independently.

5. Ride Pricing

Question:

Suppose a ride-sharing application has different pricing rules such as Peak Hour Pricing, Weekend Pricing, Long Distance Pricing, and Premium User Pricing. A single ride can have multiple applicable rules at the same time. Which relationship should we use?

Answer:

This scenario uses both inheritance and composition.

Each individual pricing rule is a type of PricingRule. Therefore, PeakHourPricing is a PricingRule, WeekendPricing is a PricingRule, and PremiumUserPricing is a PricingRule.

This makes inheritance or an interface useful because all the different pricing rules share the same abstraction. The pricing system can work with a PricingRule without knowing which specific rule it received.

However, a single ride may need to use multiple rules at the same time.

For example, imagine a premium user takes a long-distance ride during peak hours on a weekend. The pricing system may need to apply the Premium User rule, Long Distance rule, Peak Hour rule, and Weekend rule together.

We do not want to create a separate class for every possible combination, such as PremiumPeakHourWeekendLongDistanceRide. As more rules are added, the number of possible combinations would become very large.

Instead, the pricing system can contain a collection of PricingRule objects. One object can represent PeakHourPricing, another can represent WeekendPricing, and another can represent PremiumUserPricing.

This is composition because the pricing system is combining multiple independent pricing-rule objects.

Therefore, PeakHourPricing is a PricingRule, which uses inheritance or interface polymorphism, while PricingEngine has multiple PricingRule objects, which uses composition.

The important lesson is that we should not decide that an entire problem must use either inheritance or composition. Different relationships inside the same design can use different approaches.

The overall rule to remember is:

Use inheritance when we are representing different types of the same concept and need polymorphism.

Use composition when we are combining or using independent pieces of behavior.


### A more practical way to recognize inheritance vs composition

When you are given an LLD problem, do not decide only by checking whether an IS-A relationship exists. Ask whether the relationship represents the object's identity/type or whether it represents something the object uses, contains, or can change independently. If you are creating a genuine subtype that should be treated as the parent type, inheritance is a candidate. If you are giving an object some capability or behavior that can be changed, combined, enabled, disabled, or replaced independently, composition is usually a better fit. Another useful question is whether you actually need polymorphism: if different implementations need to be treated through one common abstraction, inheritance or an interface may be appropriate. This is why something like Car IS-A Vehicle can use inheritance, while Driver HAS-A Vehicle uses composition. The important point is that you should evaluate each relationship separately, rather than deciding that the whole design must use either inheritance or composition.

### Inheritance itself is not the problem

The idea behind “prefer composition over inheritance” is not that inheritance is bad or should be avoided. The problem is using inheritance for code reuse or behavior sharing when the parent-child relationship is not genuinely appropriate. Inheritance creates a stronger dependency between the parent and child, so changes in the parent can affect the child, and the child is expected to follow the parent's behavioral contract. Composition is often more flexible because the contained component can be replaced or changed without changing the type of the main object. Therefore, when both approaches can reasonably solve the problem, composition often gives us more flexibility and less coupling, but inheritance remains completely appropriate for a stable subtype hierarchy where polymorphism is actually required.

### One problem can legitimately use both inheritance and composition

A very important LLD lesson from the examples is that inheritance and composition are not mutually exclusive. For example, in the notification problem, Email, SMS, and Push can all inherit from a common NotificationChannel because they are different implementations of the same abstraction. At the same time, User can contain multiple NotificationChannel objects because the user can have several channels enabled at once. Similarly, in the pricing problem, PeakHourPricing is a PricingRule, which is an inheritance/interface relationship, while PricingEngine contains multiple pricing rules, which is composition. So you should ask about each relationship between two objects, rather than asking whether the entire problem should use inheritance or composition.

### Pricing rules can be combined sequentially, but the order can matter

In the pricing example, we discussed implementing the pricing engine by keeping multiple pricing rules and applying them one after another. For example, the current price can be passed through the first rule, then the updated price through the second rule, and so on. This is perfectly reasonable for a simplified LLD example because it demonstrates that multiple independent rules can be composed together. However, in a real pricing system, the exact calculation depends on the business requirements. If one rule adds ₹100 and another applies a 20% discount, applying them in different orders can produce different results. Therefore, the important LLD idea is not that every pricing rule must modify the price sequentially, but that the pricing system can combine multiple independent PricingRule objects without creating a separate class for every possible combination.

### The notification example has an important responsibility-separation idea

We also improved the notification design beyond simply using composition. Initially, User had separate Email, SMS, and Push objects along with separate emailEnabled, smsEnabled, and pushEnabled variables. This meant that every time a new notification channel was added, User had to be modified. We changed the design so that User keeps a collection of NotificationChannel objects, while each notification channel keeps its own enabled/disabled state. This means User only needs to know that it has notification channels and can call notify() on them. Adding a new channel such as WhatsApp does not require adding another member variable, another boolean, or another condition inside User. This is a practical example of reducing coupling and making the design easier to extend.

### A useful LLD principle from the notification example

The notification example also demonstrates that responsibility should stay with the object that owns the information. Whether Email is enabled is information about the Email notification channel, so the channel can manage that state instead of making User maintain a separate emailEnabled variable. Similarly, User is responsible for managing which channels it has and triggering notifications, while the individual channel is responsible for how that notification is delivered. This separation prevents one class from becoming responsible for every detail of every notification type.
