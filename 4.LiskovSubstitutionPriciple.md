It says:
"Objects of a subclass should be replaceable with the objects of the superclass without breaking the correctness of the code"

Which means that if we have a subclass B which is of type A, then wherever in the code we use the object of A, we should be able to replace it with the object of B, without breaking anything

> LSP is not about whether the replacement allows the code to compile. It is about whether the code behaves as per the expectation after replacement.

Example of compiled code with wrong expectations:

``` cpp
class Bird {
    virtual void fly(){
        cout<<"Bird is feeling the sky and seeing the ground!"<<endl;
    }
};

class Penguin: public Bird{
    void fly() override{
        throw Exception;
    }
}
```
Even if the code compiles here correctly when we replace the object of bird with the penguin, it is not the right way to do.
Because bird class sets the basic expectation that all the birds should fly and the client using that bird class object would be expecting a clean running code. But the penguin class would send an exception because according to the penguin class, it cannot fly, and this trait should not be working if the client code runs it. Client code wont be handling that exception. Client won't care which bird it is, it just expects the bird to behave like a bird

Its not always about being able to perform a functionality or not (like in the above example), its about being able to perform a functionality with the expectation set by the parent class. lets see an example, where the functionality could be performed but in a different way as expected

``` cpp
class Rectangle{
private:
    int height = 0, width = 0;
public:
    virtual void setHeight(int x){
        height = x;
    }
    virtual void setWidth(int x){
        width = x;
    }
    virtual int area(int x){
        return height*width;
    }
};

class Square{
public:
    void setHeight(int x) override{
        height = x;
        width = x;
    }
    void setWidth(int x) override{
        height = x;
        width = x;
    }
};

int main(){
    Rectangle* rect = new Square();
    rect->setHeight(10);
    rect->setWidth(20);
    cout<<rect->area()<<endl;
}
```
So here the area printed would be 400, while since it is a rectangle the expected area is 200

> LSP is NOT saying subclasses must behave identically

### Guidelines not to break LSP:

#### 1. Signature Rule:
##### a. Method Argument rule:
``` cpp
class Parent{
    virtual void solve(int x){}
}
class Child: public Parent{
    void solve(long long x) override{}
}
```
The parameters of the function that the child class is overriding should always have the same data type or a broader one. why? because client would be expecting x in the range of integer, but child accept till the range of long long, so we can pass anything withing the range of integer and the child would accept that without breaking the code


##### b. Return type rule:
When child class inherits the parent class, the return type of the method being overridden can be same or narrower. This is called covariance. Why? because client would be expecting let say int as the return type, if we declare the return of child class as long long, then if child class return a number greater than the range of int within long long, it would break the client code

##### c. Exception Rule:
Child class should always throw an exception that is either same as of parent class or is a subexception of the exception thrown by the parent class, becasue the client would be able to handle the subexception through the parent exception, but it cannot handle the superexception through it.

#### 2. Property Rule:

##### a. Class Invariant:
Base class decalres a rule that the child class should not break. Example, if we have made the rule that the balance in the account class cannot be negative, but in some child class (cheatAccount) of the account, balance is becoming negative, then the client class wont be able to handle it, because the child class is breaking the contract

##### b. History Constraint:
Subclass methods shouldn't be allowed the state changes what base class always allows - example, the bird - penguin example we studiedd
